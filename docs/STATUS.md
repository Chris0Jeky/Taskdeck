Post-v0.2.0 Review-queue liveness (2026-08-29):
- **An open Review page now keeps its own queue current (`#2194`, PR `#2208`).** The queue was read once on route entry and never again, so a proposal created server-side while the page sat open stayed behind "Nothing waiting. Good." until the user navigated away and back - the dogfooding run measured 115 s of `QUEUE - 0 AWAITING` against an API already reporting 1 pending. There is no realtime channel to subscribe to: `BoardsHub` is the only hub, its groups are strictly per-board, it emits only `boardMutation` / `boardPresence` / `toolStatus` over board/card/column/label entities, and `AutomationProposalService` never touches `IBoardRealtimeNotifier` - so proposal creation is silent on the wire, and the all-boards queue has no board group to join. The frontend therefore polls: `useReviewProposals` gained `startQueueRefresh`/`stopQueueRefresh` (mirroring the existing `startClock` pair, double-start guard and `onScopeDispose` included) driving a 15 s read that runs only while `document.visibilityState === 'visible'`, reads immediately on tab re-entry, stops on route leave, and is held by a surface-supplied predicate while an action is in flight or a confirm dialog is open. The background read never raises `proposalsLoading`, defers to any explicit load instead of racing it, stays silent on failure (logged, not swallowed), and preserves a `#proposal-` deep-link target that the list page omits. Both Review skins are wired, kept in step so they cannot drift. The shell's `Review - N` badge - a home-summary workload count `AppShell` fetches once at sign-in and nothing on Review ever refreshed - is now re-read whenever the awaiting count moves, via the version-guarded `refreshWorkloadCounts`; the "This week" cadence bars are a pure projection of the same proposals array and follow the refresh with no extra wiring.
- **Hardened in review before merge.** A stale read could revert a decision: every single-proposal path (approve/reject/defer/execute) patches the row locally with a new array and never touches the load counter, so a read issued before the click could land after it and write `PendingReview` back over a row whose receipt already said approved. The poll now snapshots the queue's array identity before its await and discards its answer if the reference moved, and it re-evaluates the surface guard **after** the await so a read cannot land under a dialog opened while it was in flight (the Reject dialog is bound to a computed that closes itself when its proposal leaves the list, discarding a half-typed reason). A `403` is now distinguished from a transient failure - board access was revoked, so the poll stops rather than hammering, unauthorised rows are dropped, and both skins say why, because clearing the queue silently would swap a permission failure for a fresh "Nothing waiting. Good."; a `500` leaves the queue alone and keeps polling. The deep-link pin is restored at its `createdAt` position rather than appended, so the record under review no longer jumps to the bottom of a rail that renders array order. The poll opts out of the shared three-retry interceptor and carries an `AbortController` cancelled by `stopQueueRefresh`.
- **What is both skins, and what is Paper only.** The bounded poll, the badge refresh, the polite `role="status"` live region for the awaiting count, and the revoked-access message are wired in **both** Paper and Legacy - Legacy had no badge wiring at all and no tests for any of it, and it renders no translated strings, so its copy is plain text like the rest of that file. The badge trigger is the queue **array**, not the awaiting count: watching the count missed a board-scoped view, where another board's proposal never moves the scoped number, and a decision that swaps one pending row for another. The "This week" cadence bars are **Paper only** (`ReviewMiniCadence`), and they follow the refresh with no extra wiring because they project the same proposals array.

- **The token budget is reasoning-aware, so no call site had to change.** `max_completion_tokens` caps the reasoning pass and the visible output *together*, so every budget in the tree was sized wrong the moment the default model became a reasoning model — most sharply `ProbeAsync`, whose 4-token probe could never emit "OK" and would have reported a correctly-configured API key as **unhealthy** on the *Verify LLM* button. `OpenAiLlmProvider.ResolveMaxCompletionTokens` adds a `ReasoningTokenHeadroom` of 4096 on top of the caller's visible-output budget for reasoning models only, leaving non-reasoning models byte-identical. Pre-migration SQLite auto-backup + `UPGRADING.md` (2026-08-19, `#1803`, data-trust pack part 1):
- **A schema migration no longer rewrites the user's database with no way back.** Every host mode (API, CLI, MCP HTTP, MCP stdio) goes through `SerializedMigrator`, which now takes a consistent snapshot of the SQLite file **before** `Database.Migrate()` opens any DDL connection, inside the existing cross-process migration lock. The snapshot uses SQLite's **online backup API** (`SqliteConnection.BackupDatabase`), not a file copy: Taskdeck runs in WAL mode (`#1130`), so a raw copy of the main file silently drops committed rows still sitting in an uncheckpointed `-wal`. The destination's WAL is checkpointed away before the file is moved into place, so each snapshot is a **standalone single file** — which is what makes the "backup = copy this one file" guidance in `UPGRADING.md` true. Prior art and the same conclusion for the dev-sandbox export/import path: `#1166`.
- **It runs only when it is worth running, and it fails closed.** Nothing is copied on an ordinary boot with an up-to-date schema, and nothing is copied on a first run that creates the database (there is no prior state). When migrations *are* pending against an existing file and the snapshot cannot be written, `PreMigrationBackupException` propagates out of startup and **the migration is not applied** — the error names the database, the backup directory, the cause, and the settings that resolve it. Retention *pruning* is deliberately not fail-closed (the protective copy already exists); pruning failures log a warning.
- **Configurable, with sane defaults:** `Database:Backup:Enabled` (`true`), `Database:Backup:RetainCount` (`5`), `Database:Backup:Directory` (default: a `backups/` folder next to the database file; a relative value resolves against the *database* directory, not the process working directory, because the four hosts do not share one). Documented in `docs/platform/CONFIGURATION_REFERENCE.md`; validated with `ValidateDataAnnotations().ValidateOnStart()` in `AddInfrastructure` so every host mode fails fast on a bad value.
- **`UPGRADING.md` now exists at the repo root**: where the database file lives per install mode, why Taskdeck must be stopped before copying it (WAL), the general upgrade procedure, downgrade/skip-version guidance, a v0.1.0 section (BREAKING: none) and a v0.1.1 section that now also records the Gemini-removal configuration migration, and **export documented as a headline** — full account GDPR JSON export, board JSON/CSV export, and the Settings → Export & Import view — all already shipped, pointer only.
- Coverage: 11 backend tests in `PreMigrationBackupTests`, including the ordering assertion that the snapshot's `__EFMigrationsHistory` does **not** contain the migration that was about to run, a WAL test that holds a writer connection open so the committed row is provably still uncheckpointed, standalone-snapshot (no `-wal`/`-shm`/`.tmp` sidecar) assertions, retention pruning keeping the newest N, non-managed files in the backup directory left untouched, and fail-closed (migration provably not applied after a failed backup).

Transcript evidence deep link in Paper Review (2026-08-19, `#1305` AC4):

# Muse Spark 1.3 as a delegation target — measured evaluation

**Date:** 2026-09-20 · **Model:** `muse-spark-1.3-contributor` · **CLI:** Muse Code 1.3.0 (1.3.0-R3401.1)
**Repo:** Taskdeck (T3) · **Wrapper:** `~/.claude/tools/muse_exec.py`

One session, ~17 delegations, every claim re-verified at source before it was acted on. This records what
was measured, not what was hoped.

## Verdict

**An excellent discovery engine and an unreliable judge.** Use it to find things. Never let it decide how
bad they are.

## Output

| | |
| --- | --- |
| Lens delegations completed | 13 |
| Worker delegations that landed a fix | **0 of 4** |
| PRs opened | 5 (#3272, #3273, #3276, #3277, #3278) |
| Issues filed | 2 (#3274, #3275) |
| Runs voided by coordinator error | 4 |

## O1 — The `unresolved` list outperforms the `findings` list, consistently

The single most useful operating insight. Across five lenses, the things Muse **declined** to claim were
more reliable than the things it asserted.

Both issues filed this session came from declines:

- **#3274** — quota reservation leak between `ReserveAsync` and the guarded `try`. Muse filed it
  `unresolved` because it could not prove reachability. The window is real.
- **#3275** — `MoveCard` and `ArchiveCard` create proposals with no board write check. Muse filed it as
  `unresolved` item 4, flagging that a dedicated pass was needed. That pass confirmed it, and confirmed
  that the service layer does not backstop it.

Meanwhile its HIGH findings were wrong roughly as often as right.

**Rule:** read `unresolved` before `findings`.

## O2 — Honest in the summary, overstated in the severity field

A `test-gaps` run emitted five findings, four at HIGH, each asserting a behaviour was uncovered. Three
were refuted by a ten-second grep — `AlreadyApplied` is asserted in nine test files, `IdempotencyKey` in
ten-plus.

It was not dishonest. Its own summary said: *"covered count verified 0 in this pass because no test body
was opened."* But that admission sits in the summary while the findings render at HIGH with confident
language and exact anchors. A coordinator reading only the actionable-looking list gets four false HIGHs.

**The honesty is real but filed in the wrong place.**

## O3 — Severity is scope-local

Two runs, opposite verdicts on the same code.

- Run A (`CaptureTriageService.cs`): cancellation rethrow is **checked-and-safe, by-design, test-asserted**.
- Run B (`LlmCaptureTriageExtractor.cs`): the same behaviour is **HIGH**.

Adjudicated at source: **Run A is right.** `CaptureTriageService.cs:932-935` is an explicit commented
rethrow filter, and the estimate-billing Run B objected to is dispatch-phase gated by design.

What makes this diagnostic rather than merely wrong: Run B's own `unresolved` item named the exact fact
that decides severity, recorded that it had not checked it, **and rated HIGH anyway**. The model reasons
soundly within its scope, then rates severity as though the scope boundary were the system boundary.

**Rule:** a scoped lens's HIGH is a HIGH *within that scope*. Promote it only after reading the caller it
admits it skipped.

## O4 — Budget is never the constraint; scope always is

Measured step consumption against the budget granted:

| Budget granted | Steps consumed |
| --- | --- |
| 55 | ~14 |
| 60 (clamped from 120) | ~13 |
| 100 | 13 |
| 90 | under cap |

Raising every ceiling to HARD_MAX (`max_steps 200`, `max_effort max`) changed nothing measurable. A
58-file `dead-code` sweep covered **3 files** and reported a sweep. A 14-file `test-gaps` starved and
produced four false HIGHs; the same recipe over **2 files** produced 13 findings with exact, verifiable
line numbers.

**Rule:** narrow the target. A wide lens starves regardless of budget, and it fails *quietly* —
`report_status: ok` with zero findings reads exactly like "clean".

## O5 — Where it is accurate, it is precisely accurate

`bug-hunt` cited `CaptureTriageService.cs:761/764` and `:824/827` plus the contrasting `Result.Failure`
style at `:672-676`. Every line number exact. It self-rated the finding *low* likelihood — correctly.

The `doc-drift` run produced MCP tool counts (19 total; 7 Read / 10 Propose / 2 Manage) exact down to
naming the two Manage-scoped tools, and classified two version pins `unverifiable` rather than guessing
because they lay outside its given scope. Widening the scope showed both were genuinely **stale**.
Declining to guess produced two real findings.

Best single find: `moveCard` captured an array index before an `await` and spliced it after, removing the
**wrong card** whenever anything shifted the array first (#3278).

## O6 — `--isolate` trades capability for integrity

An isolated worktree is treated as **untrusted**:

```
rules file ...AGENTS.md exists, but the workspace is untrusted, so it is skipped
Skills: 51 loaded          (a main-checkout run loads 67)
Agent delegation: auto unavailable: workspace is untrusted
```

Project rules skipped, 16 fewer skills, sub-delegation disabled. A declared `trust_workspace: true` does
**not** carry into the isolated worktree.

**Rule:** isolate when the verdict must be trustworthy while the coordinator is editing; drop it when the
lens needs depth — and then genuinely hold the checkout still.

## O7 — Workers are a bad bet; lenses are a good one

Zero of four worker delegations landed a fix. Three session crashes killed them mid-run, all while their
proving checks (`dotnet test`, minutes long) were outstanding. Lenses complete in 50-220 s and survived.

Every fix that shipped this session was implemented inline by the coordinator, first try.

**The operating split: Muse runs lenses, the coordinator implements.**

## Cost visibility

**Absent.** `muse exec 1.3.0` reports no token usage in its event stream; every run returns
`usage: unreported`. Measured indirectly: 11 runs produced 2,448 `run.output.delta` events and roughly
463 KiB of streamed output. The interactive usage meter read 0% throughout, which is consistent with the
contributor (data-use) variant being unmetered, but that was not confirmed.

## Incidents

1. **Null result from a 1,946-line doc at a 16-step budget.** Coordinator scoping error; this repo's own
   CLAUDE.md says STATUS is "section-read only". The run returned `ok` with 0 findings —
   indistinguishable from clean. Muse's `unresolved` list is what exposed it.
2. **Coordinator edited the checkout under a running lens.** `integrity: workspace_changed`,
   `report_status: untrusted`, 272 s discarded. The wrapper caught it; without that check, a confident
   `{low: 1}` review over a shifting tree would have been banked as sound.
3. **Session crash killed a four-delegation wave.** Salvaged 109 lines of correct, untracked test code
   from a worktree due for teardown. Law 7's check-before-remove is the only reason it survived.
4. **Repeat of incident 2** — three lenses voided in one wave, after explicitly promising to hold the
   tree still. The rule needs to be mechanical: commit or stash before dispatching an un-isolated lens.

## Two practices that paid for themselves

**Negative controls.** Two regression tests passed against the very bugs they named. One came from Muse's
claim (CardModal *Save* was never broken — `dirty` already guards it, because the baseline only advances
on a successful response). One was the coordinator's own: a `moveCard` spec whose loose assertions were
satisfied while an unrelated card was being destroyed. A regression test that passes against the bug it
names is worse than no test.

**Salvage before teardown.** `git worktree remove` destroys untracked files. Checking first rescued real
work once and cost nothing the other times.
